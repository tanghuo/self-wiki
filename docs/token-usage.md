# Token 用量统计

入口：内容库或 Wiki Agent 侧栏底部的「Token 用量」。可选择最近 24 小时、7 天、30 天或全部，手动刷新；按用途和模型查看总量与占比，展开最近或高消耗的 100 次调用。

覆盖 Agent 对话、自动整理每轮、图片检索描述、向量索引、向量检索和向量连接检测。记录保存在 library.sqlite3 的 token_usage 表，重启保留；不回填接入前的数据，也不记录提示词正文、图片内容或认证信息。

每次调用用稳定 ID 更新，重试生成新 ID；整理进程通过 IPC 上报，服务端统一落库，记录不依赖整理结果是否成功提交。失败、中断保留已收到的计数，重启将残留 running 标为 interrupted。强制终止可能丢失尚未送达的计数，因此未知不能视作零。

聊天使用 thread/tokenUsage/updated 的 last 初始化本轮，再累加 total 的增量，重复通知增加零；历史线程累计量不会直接当作本轮消耗。CLI 使用 turn.completed.usage，向量使用响应 usage。缓存输入是输入的子集，推理是输出的子集；两者不额外计入总量。缺失字段保留 null，汇总只含已知字段；总量覆盖率显示为「有用量 / 调用」。

辅助定位信息包括任务、内容、对话轮次、模型、耗时、初始输入字符数、附图次数、工具返回字符数、工具调用次数。字符数不是 token 数；不能据此精确分摊历史上下文、图片、系统指令或某个工具的 token。自动整理与图片描述在调用前通过 Codex 解析默认模型（有效配置优先，否则采用模型列表中的默认项），将同一名称显式传给 CLI 并写入用量及执行记录；CLI 报告模型重路由时更新名称。无法解析默认模型时停止执行并提示选择模型，避免产生无法归属的新调用。旧记录缺少模型证据，继续显示未知，不按当前配置回填。

建议先观察用途占比，再展开高消耗调用：整理轮数、输入长度、图片数量、工具返回规模可帮助找到需要优化的具体路径。该表记录用量，不推算订阅额度或账单。

验证：token-usage 单测覆盖未知字段、重复通知、多请求累计和重启恢复；chat、organization、semantic 集成测试覆盖真实子进程/HTTP 到统计接口；浏览器测试覆盖入口、空态、筛选和明细展示。

界面现在在总览、用途汇总、单次调用中分别显示缓存输入和非缓存输入。非缓存值逐条计算后求和，缺失缓存计数的已知输入另列「缓存归属未知」，避免用总输入减去不完整缓存总数。输出保持独立显示，推理是输出子集。调用明细改为紧凑表格，在返回的最近/高消耗 100 条内每页显示 10 条，详情按需展开。

整理用量还记录 `sourceCount`（本轮候选数）、`descriptionCount`（本轮带入的已有图片描述数）；`imageCount` 是实际附图数。已有描述不等于本轮重新看图。第一版节省措施与实测边界见 [用量优化记录](token-efficiency.md)。
